# Performance

How the crate is measured, what every public path is measured by, the
baselines, and where the time and the bytes go. All inputs come from one
neutral deterministic corpus (`crates/substrate-data/benches/corpus/`), so a
number here can be reproduced by anyone.

Two kinds of number appear and they are never mixed:

- **Instruction counts** (callgrind, `benches/iai.rs`): deterministic, the same
  on every machine and every run (to within a few instructions). These are the
  baselines to compare a change against.
- **Wall-clock** (criterion, every other bench): depends on the machine, its
  load and its frequency scaling; run to run noise is around 10 %. These give
  ballparks and relative orders of magnitude, nothing finer. A regression is
  claimed from instruction counts, not from criterion.

## Corpus

`benches/corpus/` is shared by every bench through `mod corpus;` (and by
`examples/sizes.rs` through `#[path]`). It is domain-neutral (users, docs,
files, projects) and generated by a fixed LCG, so it never changes between
runs.

| topic | what it is | small | medium | large |
|---|---|---:|---:|---:|
| `config` | a tree of settings: nested maps, short strings, numbers | ~0.2 KB | ~4.8 KB | ~500 KB |
| `records` | a list of records, repeated keys and repeated words | ~0.2 KB | ~5 KB | ~500 KB |
| `numbers` | lists of ints and floats | ~0.1 KB | ~5 KB | ~500 KB |
| `strings` | long and unicode strings | ~0.1 KB | ~4.7 KB | ~500 KB |
| `deep` | deep nesting, many copies | ~0.1 KB | ~4.4 KB | ~500 KB |
| `refs` | `@kind:id` references | ~0.1 KB | ~5 KB | ~500 KB |
| `blobs` | byte strings | ~0.1 KB | ~5 KB | ~500 KB |

The typed side (`corpus/typed.rs`) has `serde` + `Schema` documents of the
same three sizes: `users`, `docs`, `files`, `numbers`, `texts`, `blob`.
`corpus/shapes.rs` has the derive zoo: one type of every shape the derive
supports (scalars, enums, plain wrappers, `with` codecs, `Id<K>`, `Expand`).

## Running

Everything runs from the workspace root. A criterion file takes
`-- <filter>`, `--sample-size N`, `--measurement-time S`; the defaults are
short (`quick()`: 20 samples, 0.2 s warm-up, 0.5 s measuring) because a file
has hundreds of benchmarks.

```sh
cargo bench -p substrate-data --all-features --bench <name>   # one suite
cargo bench -p substrate-data --all-features                  # all suites
cargo bench --no-run --all-features                           # compile only (CI)
cargo bench --workspace --no-run                              # CI step, no features
cargo bench -p substrate-data --bench <name> --all-features -- --test   # run each once
```

| suite | file | what |
|---|---|---|
| `data`, `messages` | existing | the original end to end and message benches |
| `text` | `benches/text.rs` | text parse and write, patch, source, TOML |
| `binary` | `benches/binary.rs` | binary encode and decode, steps, scalars, packed lists |
| `frame` | `benches/frame.rs` | frame pack and unpack, views, steps, float kernels |
| `io` | `benches/io.rs` | frames and binary over `Read`/`Write`, streams |
| `schema` | `benches/schema.rs` | every form of every derived type, resolve, expand, dictionary |
| `reader` | `benches/reader.rs` | the `Reader` API, named types, shape descriptions, `Dictionary` |
| `model` | `benches/model.rs` | `Map`, `Value`, paths, positions, borrowed values |
| `names` | `benches/names.rs` | refs, kind names, typed strings, atoms, diagnostics |
| `scan` | `benches/scan.rs` | UTF-8 validation, memchr scans |
| `lanes` | `benches/lanes.rs` | bit-packing kernels per backend and width |
| `compare` | `benches/compare.rs` | against serde_json, ciborium, rmp-serde, postcard, bincode |
| `iai` | `benches/iai.rs` | instruction counts (callgrind) |

Variables and features:

- `LANES_WIDTHS=all` (every width 1..=32) or `LANES_WIDTHS=3,9,21` (a list)
  picks the widths of `lanes`; the default is `1,2,4,7,8,12,16,17,24,32`.
  Every available backend is measured at each width (`Backend::available()`).
- `scan` measures UTF-8 validation with and without `simd-utf8`. Run it twice:
  `cargo bench -p substrate-data --bench scan` and
  `cargo bench -p substrate-data --bench scan --features simd-utf8`. (The
  `std` and `simdutf8` rows are always both there; the `source::text` rows
  are what changes with the feature.)
- `text`'s JSON and TOML groups need `--features json` / `--features toml`
  (`--all-features` has both).

### Instruction counts

`iai-callgrind` needs valgrind and a runner of exactly the version the crate
links:

```sh
sudo apt install valgrind
cargo install iai-callgrind-runner --version 0.16.1
IAI_CALLGRIND_CALLGRIND_ARGS="--cache-sim=no" \
  cargo bench -p substrate-data --bench iai --all-features
```

293 benchmarks, about two and a half minutes. `--cache-sim=no` keeps the run
to plain instruction counts (the number quoted below). Add
`IAI_CALLGRIND_SAVE_SUMMARY=json` to get a summary per benchmark under
`target/iai/`, and compare two runs with the built-in baseline flags
(`--save-baseline=before`, then `--baseline=before`). The raw callgrind
profiles are in `target/iai/substrate-data/iai/<group>/<fn>.<id>/` and open
with `callgrind_annotate` or kcachegrind.

## Notes on how the comparison is made

- The serde formats are measured on the same typed documents the crate reads
  and writes, so the work compared is the same: encode a struct, decode it
  back and compare it with `==`. JSON is the exception to the comparison:
  serde_json without `float_roundtrip` is not bit-exact on `f64`, so the
  check on its decode skips equality (it is the default configuration a user
  has, and that is what is measured).
- bincode is version 2 (`std` + `serde`), whose configuration is
  `standard()` (varints). bincode 3 is not used.
- msgpack is measured twice: compact (positional fields) and named (a map per
  struct); the named one is what a self-describing consumer gets.
- JSON throughput in `compare` is per byte of the JSON document, so two
  formats' MiB/s are comparable per document but not across documents.
- The `Value` route (`binary::encode(&Value)`) writes no packed int and float
  lists and no `f32` narrowing; only a schema `to_bytes` does. So
  `numbers_large` is 275815 bytes as a value and 185815 as a typed document.

## Hotspots, ranked

From `callgrind_annotate` on the large samples, most to least worth the work.
Percentages are of the instructions of that benchmark.

1. **Binary encode: the interner.** `Interner::find` is 42 to 45 % of
   `binary_encode` (records, typed docs) and 33 % of the frame pack, plus 8 %
   in `memcmp`, with `Writer::string` another 14 to 17 %. Every string is
   hashed and compared against the table; a first-byte or length bucket, or a
   precomputed hash for repeated keys, is the largest single win and is also
   why `to_bytes` is 5x postcard on encode.
2. **Binary and frame decode: allocation.** `malloc`/`_int_malloc` is 19 to
   23 % of binary decode and 30 to 40 % of frame unpack: each decoded string
   is its own `String`/`Arc<str>`. `decode_ref` into an arena is already 2.3x
   faster (184 against 81 MiB/s); reading typed documents straight from
   borrowed bytes, and a shared string pool per decode, remove most of it.
3. **Text parse: `Parser::value` and allocation.** `Parser::value` is 20 %,
   malloc and free about 22 %, whitespace skipping (`ws`) 11 %, `string` 8 %,
   `string_stop` 6 %, `Map::position` and `push_unchecked` 6 %. Text parse
   costs 3 to 7x the binary decode of the same value.
4. **Typed text goes through the `Value` tree.** `to_text` and `from_text`
   are 54.6 M and 82.1 M on `docs_large` against 8.9 M and 9.8 M for binary:
   `Map::insert` is 4 %, malloc and free about 35 %. Writing and parsing
   typed documents without the intermediate tree would cut the largest gap in
   the table.
5. **Float formatting in text write.** On `numbers_large` text write is 44 M
   against 15 M for records of the same size; about 60 % is float formatting
   (grisu or dragon plus the `fmt` machinery). A shortest-round-trip printer
   without `fmt` (Ryu-style) would approach the binary cost. `write_string`
   is 39 % and `Layout::value` 19 % of the rest.
6. **Binary decode of refs.** `RefKey::is_valid` is 10 % and
   `atom::local::intern` with std SipHash `hash_one` about 11 % of the refs
   decode; `SeenKeys::insert` is 9 % on records. A faster hasher (FxHash or
   a plain length-and-bytes hash) for the intern tables and for the `Map`
   index (`HashMap<Arc<str>, usize>` with SipHash from 32 keys) is a small
   change with a measurable effect on every Map lookup above 16 keys.
7. **Varint reads.** 7 to 15 % of binary decode and `string_index` 7 to 13 %:
   a fast path for one-byte varints in the decoder loop.
8. **`patch::format`.** 1.2 M instructions on the medium sample against 156 K
   for `text::to_string`, about 8x: it builds with `format!`, `fmt` and
   intermediate `String`s.
9. **Resolver overhead.** A read with a resolver is about 4x a read with none
   and `Expand` 5x: every reference builds a `Path` and calls through
   `dyn Resolve`. Keeping the path as steps until the resolver asks for it is
   already done (`Step::Field(&'static str)`); the remainder is the `Ref`
   clone per call.

### Size overheads, ranked

1. **Tags are 17 to 35 % of every value-tree document** (35 % on `deep`,
   22 % on `refs`, 17 % on records): one byte per value. Fixed-shape
   containers (a list of maps of the same keys) can drop it; the typed frame
   already does, which is why it is 25 to 30 % smaller than `sd_binary`.
2. **Key references are 13 % of `records`/`config` and 30 % of `deep`**:
   one varint per key use. In a list of identically keyed maps they repeat
   for every element; a key-set table (sent once, indexed per map) makes them
   disappear, as the frame already does.
3. **String literals are 35 % of `records` and 66 % of `refs` (medium)**:
   unavoidable content, except where text repeats across a document
   (interning already takes care of that) or compresses (not the crate's job).
4. **Counts are 15 % of `deep`**: a count varint per container, which is one
   byte for most. Not worth removing except in the frame, which already
   shares them.
5. **The header** is 5 bytes (`SDAT` and the version), 3 % of a 150 byte
   document and nothing above 2 KB; the larger fixed cost on small documents is
   the first-use string literals.
6. **`binary::encode(&Value)` writes lists of numbers as per-item tagged
   values**: `numbers_large` is 275815 bytes against 185815 through a schema
   (-33 %). Detecting an all-int or all-float list in `encode(&Value)` would
   give the same to a dynamic document.
7. **Text** is 1.5 times the binary on records and 3.4 times on `numbers`
   pretty; pretty `deep` is 10 times its compact form. That is the form's
   purpose (people read it); no change is proposed.
